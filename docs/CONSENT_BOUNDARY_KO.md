# 동의

이 문서는 이 프로그램이 어떻게 사용자의 동의를 얻어 빌드를 진행하는 지를 설명합니다.

여기서 말하는 동의란 단순히 UI 화면에서 버튼을 눌렀다는 것만이 아니라 실제로 다운로드, 압축 해제, 패키지 설치, 빌드 명령 실행 같은 변경 작업을 시작할 수 있는 권한을 백엔드가 별도로 확인하고 관리하는 것을 말합니다.

핵심 원칙은 UI에서는 계획을 보여 주고 승인을 요청할 수 있으나 실행을 최종적으로 허가하는 쪽은 백엔드라는 점입니다. 백엔드는 실행 계획을 직접 만들고, 그 계획을 메모리 안의 검토 세션에 저장한 뒤, 승인 요청이 저장된 계획과 정확히 맞는지 확인합니다. 그 다음 백엔드 소유의 윈도우 네이티브 확인 창을 통해 사용자가 동의 했을 때만 해당 작업에 필요한 동의 값을 만듭니다.

여기서 동의 값은 전체 보호 장치 중 하나일 뿐입니다. 이 프로그램은 동의 값과 함께 계획 해시, 생성 스크립트 해시, 워크스페이스 내부 경로 검사, 심볼릭 링크 검사, 압축 해제 제한, 허용된 명령 목록, 검사/로그 기록을 함께 사용합니다.

## 전체 구성

1. 백엔드가 실행 가능한 계획을 만듦
2. 백엔드가 그 계획을 메모리 안의 검토 세션에 저장
3. UI는 계획, 경고, 최종 configure 플래그, 패키지 목록, 라이선스 영향, 동의 문구를 보여 줌
4. UI는 승인 요청을 보냄. 이 요청에는 다음 정보가 포함됨
   - 검토 세션 ID
   - 승인할 작업 이름
   - 승인한 계획 해시
   - 정확한 동의 문구
5. 백엔드는 검토 세션에 저장되어 있던 계획을 재확인
6. 백엔드는 승인 요청이 저장된 세션과 맞는지 검사
   - 세션이 존재하는지
   - 작업 이름이 같은지
   - 계획 해시가 같은지
   - 동의 문구 해시가 같은지
   - 세션이 만료되지 않았는지
   - 이미 사용된 세션이 아닌지
7. 백엔드는 저장된 계획 내용으로 계획 해시를 다시 계산
8. 백엔드는 저장된 계획이 실제로 실행 가능한 상태인지 확인
9. 백엔드가 윈도우의 네이티브 확인 창을 엶
10. 사용자가 윈도우 네이티브 확인 창에서 동의를 선택한 경우 작업별 동의 값을 생성
11. 백엔드는 저장된 계획과 그 계획에 대응하는 동의 값을 사용해 작업을 시작

## 백엔드가 호출하는 윈도우 네이티브 확인 창

UI 단계에서의 승인 호출은 최종 승인으로 실행되지 않습니다. UI는 단순히 “이 계획을 승인하려고 한다”는 요청을 보냅니다.

백엔드는 저장된 검토 세션이 유효한지, 저장된 계획이 실행 가능한지, 다시 계산한 계획 해시가 일치하는지 확인하며, 윈도우 네이티브 확인 창을 호출합니다. 이 확인 창에서 해당 작업에 맞는 동의 타입을 받은 경우에만 변경 작업을 시작합니다.

윈도우 네이티브 확인 창을 WebView가 아니라 백엔드가 직접 소유하는 이유는 프런트엔드 메시지가 조작되거나, JavaScript 호출이 변경되거나, 로컬 상태 값이 재사용되거나, WebView 개발자 도구 호출이 이루어진 경우 등에 사용자가 동의한 것으로 잘못 실행되는 것을 막기 위함입니다.

## 확인 창에서 거절한 경우

네이티브 확인 창의 기본값은 `No`입니다.

백엔드는 `Yes`가 아닌 모든 결과를 거절로 처리합니다. 여기에는 `No`, `Cancel`, Escape 키, 창 닫기, 대화상자 오류, 빈 결과, 예상하지 못한 버튼 문자열이 모두 포함됩니다.

사용자가 네이티브 확인 창을 취소하거나 거절한다고 해도 검토 세션은 사라지지 않는다. 세션이 만료되지 않았다면 동일한 계획으로 다시 확인을 시도할 수도 있다. 검토 세션은 백엔드 네이티브 확인이 성공한 뒤에만 승인됩니다.

## 검토 세션의 저장 방식

검토 세션은 네이티브 확인이 성공했을 경우 단 한 번만 사용됩니다. 이미 사용한 검토 세션 ID를 다시 사용할 경우 실패합니다.

현재 검토 세션의 유효 시간은 30분입니다. 작업 이름, 계획 해시, 동의 문구가 모두 맞다고 하더라도 세션이 만료될 경우 승인되지 않으며 실행되지 않습니다.

검토 세션은 메모리에만 저장됩니다. 프로그램을 닫거나 다시 시작하면 승인되지 않은 검토 세션은 사라집니다.

## 승인되는 작업과 동의 값

승인 요청은 백엔드의 승인 메소드 안에서 동의 값으로 변환됩니다. 승인된 계획 하나가 동의 값을 여러 개 생성할 수도 있으며, 이 동의 값들은 동일한 작업 이름, 동일한 계획 해시, 동일한 동의 문구로 분류 취급됩니다.

| 승인된 작업 | 네이티브 `Yes` 이후 만들어지는 동의 값 |
| --- | --- |
| 개인용 MSYS2 도구 체인 준비 | `Msys2DownloadConsent`, `ArchiveExtractionConsent`, `PacmanInstallConsent` |
| FFmpeg 빌드 | `FfmpegSourceDownloadConsent`, `ArchiveExtractionConsent`, `PacmanInstallConsent`, `CommandExecutionConsent` |

MSYS2 다운로드 동의는 같은 도구 체인 준비 계획에 포함된 MSYS2 서명 파일과 서명 키 다운로드에도 함께 사용됩니다.

FFmpeg 소스 다운로드 동의는 같은 FFmpeg 빌드 계획에 포함된 FFmpeg 서명 파일, 서명 키, 준비 라이브러리의 소스 다운로드에도 함께 사용됩니다.

## 사용 중인 동의 타입

현재 실제 승인 단계에서 사용되는 동의 타입은 다음과 같습니다.

- `Msys2DownloadConsent`
- `FfmpegSourceDownloadConsent`
- `ArchiveExtractionConsent`
- `PacmanInstallConsent`
- `CommandExecutionConsent`

코드에는 `WorkspaceDeletionConsent`도 정의되어 있습니다. 다만 현재 정리와 삭제 경로는 이 타입을 실제 승인 경계로 사용하지 않습니다. 현재 상태에서는 예약되어 있는 정의입니다.

동의 값을 단순한 `true`/`false` 값으로 두지 않고 타입이 있는 값으로 정의한 것은 보호 대상 함수가 전달 받은 동의 값이 정확히 어떤 종류의 작업, 어떤 작업 이름, 어떤 계획 해시에 대해 만들어진 것인지 검사할 수 있게 하기 위함입니다.

## 보호되는 작업

현재 아래의 변경 작업은 동의/승인 과정을 통해 관리됩니다

- `DownloadMsys2WithConsent`를 통한 MSYS2 압축 파일, 서명 파일, 서명 키 다운로드
- `DownloadFfmpegSourceWithConsent`를 통한 FFmpeg 소스 압축 파일, 서명 파일, 서명 키, 준비 라이브러리 소스 다운로드
- `ExtractArchiveWithConsent`를 통한 승인된 압축 해제
- `RunPacmanWithConsent`를 통한 승인된 패키지 설치
- `RunCommandWithConsent`를 통한 승인된 configure, make, 준비 라이브러리 스크립트 실행

이 함수들은 작업을 수행하기 전에 전달받은 동의의 종류, 승인된 작업 이름, 승인된 계획 해시가 맞는지 확인합니다.

## 보호되지 않는 작업

모든 백엔드 명령과 파일 작업이 동의 값으로 관리되지는 않습니다.

변경 작업이 아니거나 보조 성격의 작업은 현재 동의 값으로 관리하지 않습니다. 이런 작업에 있어서는 고정 값이나 경로 검사로 제한관리가 제한되어 있습니다.

- 결과 폴더, 보고서, 로그 폴더, 로컬 로그 파일 열기
- 개인용 MSYS2 환경의 패키지 상태 읽기
- 고정된 검사 명령으로 빌드된 `ffmpeg.exe`와 `ffprobe.exe` 확인하기
- 정리 과정에서 개인용 MSYS2 백그라운드 에이전트 중지하기

정리 및 삭제도 현재는 `WorkspaceDeletionConsent`를 사용하지 않습니다. 이미 승인된 작업의 후속 처리이거나 명시적인 백엔드 작업으로 실행되기 때문이며, 워크스페이스 내부 경로 검사, 실제 경로 검사, 루트 경로 거부, 심볼릭 링크 검사, 제한적으로 구성된 대상 경로에 의존하기 때문입니다.

## 정리와 삭제

현재 정리 작업은 별도의 삭제 동의로 보호되는 구조가 아니라, 승인된 작업의 범위와 워크스페이스 내부 경로 제한 안에서 실행되는 구조입니다.

- 도구 체인 준비 실패 후 정리
- FFmpeg 빌드 실패 후 정리
- 새 빌드 결과를 복사하기 전에 기존 FFmpeg 산출물 파일 제거
- 새 개인용 MSYS2 도구 체인을 준비할 때 이전 개인용 MSYS2 디렉터리 제거
- 개인용 도구 체인 설치 디렉터리를 명시적으로 제거

이 경로들은 임의의 파일을 지우지 않습니다. 대상이 선택된 워크스페이스 안에 있는지 확인하며, 위험한 루트 경로는 다루지 않으며, 필요한 곳에서는 안전하지 않은 심볼릭 링크를 따르지 않고, 프런트엔드에서 받은 자유 입력이 아니라 워크스페이스 구조에서 삭제 대상을 별도로 관리합니다.

## 다운로드 경계

승인된 다운로드라도 실행 시점에서 다시 검사합니다. 특히 다음 조건을 확인합니다.

- URL이 HTTPS인지
- 대상 경로가 선택된 워크스페이스 안에 있는지
- 실제 대상 경로도 선택된 워크스페이스 안에 머무르는지
- 임시 다운로드 경로도 선택된 워크스페이스 안에 있는지
- 예상 파일 크기의 최소값과 최대값 제한을 지키는지
- 기존 파일을 재사용할 때 계획이 재사용을 허용하고, 기대 SHA-256 해시와 실제 해시가 일치하는지
- 계획에 SHA-256 해시가 있으면 그 값을 검증하는지

일부 다운로드 경로의 경우 허용 목록에 없는 호스트라고 해서 항상 즉시 차단되지는 않으며 로그에 경고를 남깁니다. 대신 HTTPS, 대상 경로 제한, 크기 제한, 계획에 정의된 해시/서명 검증을 통해 다운로드가 안전할 수 있도록 확인 절차를 밟습니다.

## 압축 해제

승인된 압축을 해제할 때도 실행 시점에서 다시 검사합니다. 특히 다음 조건을 확인합니다.

- 압축 파일이 선택된 워크스페이스 안에 있는지
- 압축 파일의 실제 경로도 선택된 워크스페이스 안에 있는지
- 압축을 풀 대상 디렉터리가 선택된 워크스페이스 안에 있는지
- 대상 디렉터리 정책을 만족하는지
- 압축 파일 수, 전체 해제 바이트 수, 단일 파일 바이트 수가 제한을 넘지 않는지
- 해제된 경로가 대상 디렉터리 밖으로 빠져나가지 않는지
- 안전하지 않은 심볼릭 링크 동작이 거부되는지

따라서 단순 동의만으로 무조건 압축 파일이 해제되지 않습니다. 동의할 경우 승인된 계획에 대해 이러한 종류의 작업을 허가하고, 뒤 이은 압축 해제 검사는 실제 압축 파일이 어디에 무엇을 쓸 수 있는지 제한합니다.

## 명령 실행

파일을 변경하는 빌드 명령은 `RunPacmanWithConsent`와 `RunCommandWithConsent`를 통해 동의 값을 가집니다.

명령 실행은 추가로 명령 계획 검사를 받습니다.

- 실행 파일 경로가 워크스페이스 안에 있어야 함
- 실행 파일의 실제 경로도 워크스페이스 안에 있어야 함
- 작업 디렉터리가 워크스페이스 안에 있어야 함
- 작업 디렉터리의 실제 경로도 워크스페이스 안에 있어야 함
- MSYS2 루트 디렉터리가 있으면 워크스페이스 안에 있어야 함
- 실행 로그 디렉터리가 있으면 워크스페이스 안에 있어야 함
- 실행 파일의 기본 이름이 명령 계획의 허용 목록에 있어야 함
- 실행 파일 경로에는 셸 메타문자가 없어야 함
- 인자에는 널 바이트가 없어야 함

이 검사는 승인된 빌드 단계가 개인용 워크스페이스 밖을 사용하는 임의 명령으로 바뀌지 못하게 함을 목적으로 합니다.

## 생성 스크립트

빌드에 필요할 경우 생성된 스크립트는 엄격히 관리됩니다.

백엔드가 스크립트를 실행하는 명령을 준비할 때 명령 계획에는 다음 정보가 기록됩니다.

- 스크립트 종류
- 승인된 스크립트 파일 경로
- 승인된 스크립트 SHA-256 해시

실행 직전에 스크립트 파일이 워크스페이스 안에 있는지, 실제 스크립트 경로도 워크스페이스 안에 있는지, 명령 인자 안에 해당 스크립트 경로가 들어 있는지를 확인합니다. 그 다음 스크립트 내용을 읽고 SHA-256 해시를 다시 계산합니다. 내용이 승인된 해시와 다르면 실행은 자동으로 거부됩니다.

검사가 끝났을 때 스크립트 파일 경로 인자를 표준 입력 실행 방식으로 바꿉니다. 이렇게 하여 승인된 스크립트 내용이 확인된 뒤 다른 스크립트가 몰래 실행되는 것을 막습니다.

## 요약

UI는 계획을 보여 주고 승인을 요청할 수 있습니다. 하지만 저장된 계획, 계획 해시, 기대 동의 문구, 네이티브 확인, 동의 값 생성, 최종 실행 검사 권한은 백엔드가 소유합니다.

또한 한번 승인된 계획의 재사용은 거부됩니다. 백엔드는 검토 세션을 저장하고, 만료 여부를 확인하며, 네이티브 확인이 성공한 뒤에는 해당 세션을 만료된 것으로 변경합니다.
