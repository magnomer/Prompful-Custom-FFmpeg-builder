투명성 모델

이 문서는 이 프로그램이 빌드 과정에서 중요한 작업을 어떻게 드러내고, 어떤 위치에서 검토할 수 있게 만드는지 설명합니다.

이 프로그램은 FFmpeg를 빌드하기 위해 소스 아카이브를 다운로드하고, 압축을 풀고, MSYS2 패키지를 설치하고, 셸 스크립트를 생성한 뒤, 빌드 명령을 실행하고, 결과물을 복사하며, 로그와 보고서를 남깁니다. 이런 작업은 사용자의 컴퓨터에서 실제 파일과 프로세스를 다루기 때문에 숨겨진 편의 기능처럼 처리해서는 안 됩니다.

여기서 말하는 투명성은 “보이기 때문에 안전하다”는 뜻이 아닙니다. 중요한 작업이 소스 코드에서 찾기 쉽고, 실행 전에 검토 가능하며, 실행 후에는 로컬 기록으로 확인 가능해야 한다는 뜻입니다.

1. 이 문서가 다루는 범위

이 프로그램의 투명성 모델은 크게 네 가지 층으로 나뉩니다.

층 드러내는 내용 위치
소스 구조 다운로드, 압축 해제, 계획 생성, 명령 실행, 스크립트 생성, 작업 공간 검사, 검사 기록을 어느 코드가 담당하는지 internal/ 아래 Go 패키지, frontend/src/ 아래 프런트엔드 코드, scripts/ 아래 검사 스크립트
검토 데이터 실행 전에 무엇을 다운로드하고, 설치하고, 준비하고, configure에 넘기고, 실행하고, 복사할 것인지 백엔드가 만든 검토 객체와 프런트엔드의 승인 화면
실행 증거 승인된 작업 중 실제로 어떤 일이 일어났는지 실시간 로그, 저장된 로컬 로그, 빌드 보고서, 로컬 검사 JSONL
경계 검사 중요한 작업이 예상한 소스 위치에 있는지 scripts/security-scan.go, scripts/security-scan.ps1

프런트엔드는 계획과 경고, 로그, 보고서를 보여 주므로 투명성 모델의 일부입니다. 그러나 프런트엔드가 곧 보안 경계인 것은 아닙니다. 최종 승인, 검토 세션, 동의 값, 실제 실행 권한은 백엔드가 소유합니다.

4. 검토와 승인 화면에서 보여야 하는 것

변경을 일으키는 빌드 작업은 먼저 계획으로 만들어지고, 사용자가 그 계획을 확인할 수 있어야 합니다. 승인 화면의 목적은 실행 전에 중요한 영향을 숨기지 않는 것입니다.

검토 화면에는 상황에 따라 다음 정보가 포함될 수 있습니다.

  • 작업 이름
  • 계획 해시
  • 예상 동의 문구
  • 실행될 작업 목록
  • 심각도별 경고
  • 다운로드 URL과 검증 방식
  • MSYS2 패키지 이름
  • 선택한 라이브러리 연동 항목
  • 선택한 configure 옵션
  • 라이브러리에서 생성된 configure 플래그
  • 사용자가 직접 입력한 추가 플래그
  • 최종 configure 플래그
  • 생성 스크립트와 스크립트 해시
  • 파생된 라이선스 프로필
  • PATH 변경 여부, 관리자 권한 필요 여부, 기존 MSYS2 사용 여부, 파일 삭제 여부

프런트엔드는 이 정보를 보여 주고 승인 요청을 보냅니다. 그러나 승인 요청을 보냈다는 사실만으로 실행 권한이 생기지는 않습니다. 백엔드는 자신이 저장한 검토 세션과 승인 요청을 대조하고, 마지막으로 Windows 네이티브 확인 창을 띄운 뒤, 그 확인이 성공했을 때만 타입이 있는 동의 값을 만들고 작업을 시작합니다.

검토 세션은 프런트엔드 상태가 아닙니다. 세션 ID, 계획 해시, 동의 문구 해시는 백엔드가 소유합니다. 프런트엔드가 체크박스나 로컬 상태를 유지하고 있다는 이유만으로 동의가 성립하지 않습니다.

5. 동의가 필요한 명령과 보조 명령

이 프로그램은 빌드/설치 명령과 보조 명령을 구분합니다.

빌드 결과나 도구 체인 상태를 바꾸는 명령은 타입이 있는 동의와 관리 실행 계층을 사용합니다. 대표적인 예시는 다음과 같습니다.

  • RunPacmanWithConsent를 통한 MSYS2 패키지 설치
  • RunCommandWithConsent를 통한 FFmpeg configure 스크립트 실행
  • RunCommandWithConsent를 통한 make 스크립트 실행
  • 승인된 빌드 계획에 포함된 라이브러리 준비 명령 실행

반면 어떤 명령은 빌드 계획을 실행하는 명령이 아니라, 앱의 보조 동작입니다. 이런 명령은 CommandExecutionConsent 작업으로 설명하지 않습니다. 예시는 다음과 같습니다.

  • 결과 폴더 열기
  • 생성된 보고서 열기
  • 로그 폴더 열기
  • 저장된 로컬 로그 파일 열기
  • 고정된 pacman 인자로 설치된 패키지 목록 확인하기
  • -version, -encoders 같은 고정 인자로 빌드된 FFmpeg 바이너리 확인하기
  • 정리 중 개인용 MSYS2 보조 프로세스 중지하기

보조 명령도 임의 명령 실행처럼 다뤄서는 안 됩니다. 가능하면 고정 인자를 사용하고, 앱이 소유한 경로나 작업 공간 검사로 대상을 제한해야 합니다. 또한 이런 동작은 internal/app/*.go 안에서 추적 가능해야 합니다.

6. 생성 스크립트의 투명성

FFmpeg 빌드에는 셸 스크립트가 필요합니다. 이 프로그램은 그 스크립트를 내부 구현 세부사항으로만 취급하지 않습니다.

스크립트 계층은 패키지 설치, configure, make, 선택된 라이브러리 준비 작업에 필요한 스크립트 본문을 생성합니다. 앱은 생성된 스크립트를 작업 공간 안의 앱 소유 위치에 쓰고, SHA-256 해시를 계산한 뒤, 그 해시를 실행 계층에 전달합니다.

실행 계층은 스크립트를 실행하기 전에 파일 내용이 승인된 SHA-256 해시와 여전히 일치하는지 확인합니다. 빌드 스크립트는 통제된 MSYS2 Bash 환경을 통해 실행됩니다. 따라서 생성 스크립트의 내용, 파일 경로, 해시는 모두 검토 가능한 빌드 경계의 일부입니다.

일부 호환성 우회는 계획 단계가 아니라 생성된 스크립트 안에서 처리됩니다. 예를 들어 --enable-libsvtjpegxs, --enable-liblensfun, --enable-vapoursynth 같은 플래그는 configure 스크립트 안에서 별도 검사를 거친 뒤, 선택된 FFmpeg 소스가 기대하는 API를 설치된 패키지가 제공하지 않으면 경고를 남기고 해당 플래그를 제거할 수 있습니다. 이것은 스크립트 실행 시점의 특정 호환성 처리이지, 모든 사용 불가 라이브러리에 적용되는 일반적인 계획 단계 규칙이 아닙니다.

7. 다운로드, 압축 해제, 작업 공간 경계

다운로드는 다운로드 계층에서 처리되며, 실행 계획과 연결됩니다. 다운로드 경계에는 다음 요소가 포함됩니다.

  • HTTPS 소스 URL만 허용
  • 작업 공간 내부 저장 경로 검사
  • 파일 크기 제한
  • 리디렉션 제한
  • 선택적 SHA-256 검증
  • 기대 해시가 있는 경우, 기존 파일은 해시가 맞을 때만 재사용
  • 알려진 소스 계열에 대한 호스트 allowlist 경고

서명 파일과 서명 키 다운로드는 별도의 무관한 다운로드가 아니라, 승인된 소스/도구 체인 다운로드 작업의 일부로 취급됩니다. 예를 들어 FFmpeg 소스 아카이브, .asc 서명, 서명 키 다운로드는 같은 FFmpeg 소스 다운로드 경계 안에서 처리됩니다.

압축 해제는 압축 해제 계층에서 처리합니다. 이 계층은 대상 위치, 아카이브 형식, 풀린 파일의 총 크기 제한, 경로 탈출 위험을 확인합니다. 작업 공간 검사와 심볼릭 링크 거부는 타입이 있는 동의와 별개의 두 번째 보호층입니다. 다운로드, 압축 해제, 스크립트 생성, 파일 복사, 삭제가 작업 공간 밖으로 벗어나지 않도록 제한합니다.

8. 로그, 보고서, 검사 기록

이 프로그램에는 서로 다른 성격의 실행 증거가 있습니다. 모두 “로그”라고 뭉뚱그려서는 안 됩니다.

실시간 프로세스 로그 작업이 실행되는 동안 stdout/stderr를 보여 줌
저장된 로컬 로그 기록 이전 로컬 로그를 보존하고 나중에 다시 볼 수 있게 분류함
빌드 보고서 JSON 선택 라이브러리, 플래그, 라이선스 프로필, 출력 파일, 크기, SHA-256 해시 같은 빌드 결과 메타데이터를 기록함
검사 JSONL 승인된 실행에서 주요 이벤트가 어떤 순서로 일어났는지 로컬 증거로 남김

검사 파일은 원격 텔레메트리 채널이 아닙니다. 승인된 작업, 사용된 계획, 주요 실행 이벤트를 사용자의 로컬 환경 안에 남기기 위한 기록입니다.

빌드 보고서와 검사 로그는 서로 보완 관계입니다. 보고서는 완성된 산출물과 빌드 설정을 설명하는 데 초점을 두고, 검사 로그는 승인된 작업의 실행 과정에 초점을 둡니다.

9. 프런트엔드와 백엔드의 책임 분리

프런트엔드는 화면 표시, 선택 상태, 현지화, 저장된 UI 상태, 검토 화면 구성을 담당합니다. 백엔드에 작업을 요청할 수는 있지만, 실행을 허가하는 주체는 아닙니다.

백엔드가 소유하는 것은 다음과 같습니다.

  • 계획 생성
  • 검토 세션 생성과 만료 처리
  • 동의 문구 해시
  • 계획 해시 검증
  • 네이티브 확인 창
  • 타입이 있는 동의 값 생성
  • 다운로드, 압축 해제, 패키지 설치, 명령 실행, 산출물/보고서 작성
  • 작업 공간 경로 검사
  • 취소와 정리 동작

이 분리가 중요한 이유는 UI가 오래된 상태이거나, 번역되어 있거나, 화면 구조가 바뀌어도 백엔드가 실행할 수 있는 내용은 별도로 검증되어야 하기 때문입니다. 최종적으로 실행되는 것은 프런트엔드의 표시 상태가 아니라, 백엔드가 검증한 계획과 동의 값입니다.

10. 정적 경계 검사기

정적 검사기는 작은 텍스트 기반 소스 검토 도구입니다. Go 소스 파일에서 다음과 같은 중요한 기초 작업을 찾습니다.

  • 프로세스 시작
  • HTTP 클라이언트/요청 사용
  • 재귀 삭제
  • 파일 삭제
  • 파일 이름 변경
  • 직접 파일 쓰기
  • 셸 문자열 실행
  • unsafe Go 사용

검사기는 발견된 위치를 allowlist와 비교합니다. allowlist는 해당 작업을 소유할 것으로 예상되는 소스 위치 목록입니다. 그래서 중요한 기초 작업이 예상하지 못한 파일에 새로 등장했을 때 이를 찾는 데 유용합니다.

다만 이 검사기는 형식적인 증명 시스템이 아닙니다. allowlist는 실제 소스 구조와 계속 맞춰져야 합니다. 현재 소스는 앱 오케스트레이션을 internal/app/*.go로 나누었지만, 검사기 규칙 일부는 예전 경로 가정을 아직 포함하고 있습니다. 따라서 검사기 불일치는 두 가지 중 하나일 수 있습니다.

  1. 실제로 새로운 경계 문제가 생긴 경우
  2. 의도적인 소스 구조 변경 이후 검사기 규칙이 따라오지 못한 경우

이 문서를 개정한 시점에서는, 정적 검사기를 “유용한 경계 검토 도구”로 보되, 그 결과를 현재 소스 구조가 문서화된 경계와 완전히 일치한다는 증거로 쓰기 전에는 allowlist 정비가 필요합니다.

11. 경계 변경을 검토할 때 볼 것

소스 변경을 검토할 때는 다음 사항이 중요합니다.

  1. 새로운 다운로드, 압축 해제, 명령 실행, 삭제, 쓰기, 이름 변경이 그 작업을 담당하는 기존 패키지 안에 있는가?
  2. 빌드나 설치를 변경하는 작업이라면 검토된 계획과 타입이 있는 동의에 묶여 있는가?
  3. 보조 명령이라면 인자가 고정되어 있고 대상 경로가 제한되어 있는가?
  4. 생성 스크립트는 쓰기, 해시 계산, 실행 전 검증을 거치는가?
  5. 파일 시스템 변경 주변에 작업 공간 내부 경로 검사와 심볼릭 링크 검사가 유지되는가?
  6. 검토 화면이 패키지, 라이브러리, 플래그, 라이선스 영향, 경고, 삭제/관리자 권한/PATH 관련 표시를 사용자에게 충분히 보여 주는가?
  7. 로그, 보고서, 검사 기록이 로컬에서 이해 가능한 형태로 남는가?
  8. 정적 검사기가 불일치를 보고한다면, 그것이 실제 경계 확장인지 아니면 오래된 검사 규칙 때문인지 구분했는가?
